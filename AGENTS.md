# AGENTS.md — Augmented Cooking web client

Operating manual for AI coding agents working in `clients/web/` (the React SPA).
Read this file before making any changes. When this file conflicts with the code, follow the code's existing patterns and update this file.

## 1. What this app is

**Augmented Cooking** — an AI-assisted cooking platform. Home cooks search, create, organize, share, and fork recipes; generate recipes and edit them with AI; get AI nutritional analysis; chat with a cooking assistant; plan meals in a weekly calendar; and generate shopping lists. Social features: favorites, star ratings, threaded reviews with images, report flow, private/public collections. Recipes can be imported from external URLs (backend-side scraping). Cook mode supports portion scaling, unit conversion, and persistent ingredient check-off. Moderator and admin panels cover moderation, tickets, users, plans, AI models, and metrics.

**Roles:** `user` · `moderator` (moderate recipes, reviews, reports, tickets) · `admin` (users, plans, AI models, system config, metrics, bug reports). The role comes from `profiles.role` (generated DB enum `app_role`), surfaced through `useAuthUser()`.

**Subscriptions:** Free (limited AI actions, economy models) and Premium (unlimited AI, advanced models, token quota with top-ups). **Quotas and limits are backend-enforced — never hardcode plan limits into frontend logic.**

**Relationship to other services** — this app has **two** data paths (both verified in the code):

1. **Supabase** (PostgREST + GoTrue auth + Storage + RPCs, via `supabase-js`) — the primary data layer for all app data: recipes, reviews, collections, favorites, profiles, plans, AI model catalog, tickets, moderation. RLS is the enforcement layer.
2. **NestJS REST backend** via the shared axios client (`src/api/client.ts`) — used for the AI/scraping/order/billing endpoints only (`/ai/*`, `/recipes/import`, `/orders`, `/billing/*`). **That backend exists** (NestJS at `../../server`) and implements the frozen contract in `docs/API_ENDPOINTS.md` (error convention: failures return an HTTP status with a `{ message: string }` body). Point `VITE_API_URL` at it; while it is unreachable those surfaces fail with visible, handled errors. Shipped responses are a superset of the doc — `tokensUsed` rides along on the AI responses, and the recipe draft has no `caloriesPerServing` (calories live only in the analyze-nutrition response) — the client schemas already tolerate this; don't trim fields to match the doc. Known gap: the profile's "preferred model" (`profiles.ai_model_id`) is stored but no AI surface sends `modelId` yet.

The backend service lives outside this app at `../../server` (NestJS, has its own AGENTS.md). **Frontend work never touches it.**

## 3. Golden Rules

1. **Code only.** No git, no commands, no installs, no `.env` (see Your Scope).
2. **Never edit `src/routeTree.gen.ts`.** It's generated by the router plugin when the dev server runs. If you add/move route files, note in your response that the dev server must be restarted to regenerate it.
3. **Server state lives in TanStack Query only.** Never copy API data into Zustand, component state, or context. (Dexie-backed local data is the exception — it's local-first by design — but even it is read through feature hooks + query keys, see Data Flow.)
4. **React Compiler is on — do not add `useMemo`, `useCallback`, or `React.memo`.** Write plain code; the compiler memoizes it.
5. **Validate at every boundary with Zod:** service responses, URL search params, form input. Never `as`-cast data you haven't parsed.
6. **Use Mantine components.** If Mantine has it (button, modal, select, table, tooltip, notification), use it — don't hand-roll.
7. **No new dependencies** without explicit human approval.
8. **React 19 conventions:** function components only, `ref` is a regular prop (no `forwardRef`), no class components.
9. **All HTTP goes through the two shared clients** — `src/api/client.ts` (axios, REST backend) and `src/lib/supabase/client.ts` (Supabase). Never `fetch` directly, never a second axios instance, never a second Supabase client.

### Feature module anatomy (canonical: `features/recipes`)

```
features/<name>/
├── api/routes.ts        # REST endpoint paths for this feature (e.g. RECIPES_API_ROUTES) — if it has any
├── components/          # PascalCase.tsx (+ folder components with index.ts) + index.ts barrel
├── constants/           # e.g. RECIPES_SEARCH_PATH
├── hooks/               # useXxx.tsx — one per operation; also exports useXxxOptions queryOptions factories for loaders
├── query-keys/keys.ts   # query key factory — single source of truth (recipeKeys)
├── services/            # one verb-named file per operation (fetchRecipes.ts, updateRecipe.ts, …)
├── store/               # Zustand stores, only if the feature has UI state (cookMode.store.ts)
├── types/               # feature types + schemas/ (Zod) + recipeSelect.ts
└── utils/               # feature helpers (pagination/, units.ts, draft.ts)
```

- Every folder gets an `index.ts` barrel; the feature root `index.ts` re-exports the public surface. Consumers import from `@features/recipes` (or another feature's barrel) — **never from deep paths inside another feature**. Shared folders (`api/`, `components/`, `config/`, `lib/`, `types/`, `utils/`) only receive genuinely generic code with real consumers.
- `features/auth` nests schemas inside `components/<form>/schemas/` — an accepted older variant; prefer the `recipes` layout for new code.
- Placement rule: one consumer → keep it in that feature. Two features need the same thing → promote to a shared folder and update both consumers.

### Recipes — the one shared recipe shape

Every query returning recipe rows must select the shared `RECIPE_SELECT` (from `features/recipes/types`; `RECIPE_SELECT_NUTRITION_INNER` when filtering on `recipe_nutrition` columns) and validate against `fullRecipeSchema`. Select string and schema change together — a mismatch only fails at runtime inside `.parse()`. There is no "list/summary" recipe shape. Only id-only/count aggregates and single-column reference embeds (e.g. `recipes(title)`) may use minimal selects. Keep select strings as literal constants — supabase-js parses them at the type level; runtime-built strings (`join`, interpolated `string`) collapse the result into a `ParserError` type.

### Creating a new page

1. Build the page component inside the owning feature's `components/` (with `XxxPending`/`XxxError` siblings if the route needs route-level states — see `RecipeExplorerPage`).
2. Add a thin route file in the right group under `src/routes/` (see Routing): `validateSearch` if the URL carries state, a `loader` that prefetches via `context.queryClient.query(<feature>Options(...))`, `pendingComponent`/`errorComponent`, and a component that delegates to the feature component. **Route files hold no UI** — duplicated UI between public and protected twins goes in one shared feature component.
3. New endpoint used? Add an MSW handler (`src/test/handlers/`).
4. Tell the human to restart the dev server so `routeTree.gen.ts` regenerates.

### Creating a new feature

Mirror `features/recipes`: create the folders the feature actually needs (don't pre-create empty ones), barrels included, then follow "Creating a new page". Query keys in `query-keys/keys.ts`, Zod schemas in `types/schemas/*.schema.ts`, services own HTTP + validation.

## 9. Routing — TanStack Router (file-based)

Route files live directly in `src/routes/`, grouped by audience with **pathless layout routes** (`_auth.tsx`, `_public.tsx`, `_protected.tsx`, `_moderator.tsx`, `_admin.tsx`); pages nest under a folder named after the group. `autoCodeSplitting: true`, so every route is lazy-loaded already. Co-located `*.test.tsx` files under `routes/` are ignored by the router plugin (`routeFileIgnorePattern` in `vite.config.ts`).

| Group        | Guard (in the group's `beforeLoad`)                                                              | Routes                                                                                                                                     | Feature     |
| ------------ | ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ | ----------- |
| `_auth`      | none at group level                                                                              | `/login`, `/sign-up`, `/verify-otp`, `/forgot-password` (+ `/confirm`), `/update-password`                                                   | auth        |
| `_public`    | none                                                                                              | `/` (landing), `/recipes` (explorer), `/recipes/$id` (detail)                                                                                | public      |
| `_protected` | session required, else `/login?next=<href>`; exemption: `/recipes/search` falls through (see below) | `/recipes/search`, `/recipes/create`, `/recipes/generate`, `/recipes/import`, `/recipes/$id/edit`, `/recipes/$id/cook`, `/my-recipes`, `/favorites`, `/collections` (+ `/$id`), `/ai-assistant`, `/planner`, `/shopping-list`, `/subscription`, `/profile`, `/support` | respective features |
| `_moderator` | session + `profiles.role` ∈ {moderator, admin}, else → `/recipes`                                 | `/mod` (index → `/mod/dashboard`), `/mod/dashboard`, `/mod/reviews`, `/mod/tickets`                                                          | moderator   |
| `_admin`     | session + `profiles.role = admin`, else → `/recipes`                                              | `/admin` (index → `/admin/dashboard`), `/admin/dashboard`, `/admin/users`, `/admin/recipes`, `/admin/settings`, `/admin/reports`              | admin       |

The `_protected` layout provides the app shell (header + sidebar nav, user menu, color-scheme toggle); `_public` provides a header/footer marketing shell; `_admin`/`_moderator` shells add their role badge and nav. `_auth` is a plain centered layout.

**Auth/role guards belong in the group's layout `beforeLoad` — never in component effects.**

### Route twins and auth redirects

Some pages exist in a public and a protected version at **different** URLs sharing **one** implementation — never create two file routes with the same URL path (TanStack Router resolves one winner and silently drops the other):

- `/recipes` (public) ⇄ `/recipes/search` (protected) — both render `RecipeExplorerPage` from `@features/recipes`.
- `/recipes/$id` (detail) exists **only** in the public group and serves signed-in users too; `/recipes/$id/edit` and `/recipes/$id/cook` are protected-only. The edit route throws a redirect to the public detail for non-owners — replicate that ownership check for any new owner-only page.

Redirect rules (all implemented in `beforeLoad`, all **await `supabase.auth.getSession()` first** so no decision is made while the session is still restoring):

```ts
// _public/recipes: signed-in visitors go to the protected twin, query string intact
beforeLoad: async ({ search }) => {
  const { data } = await getSupabaseBrowserClient().auth.getSession();
  if (data.session) throw redirect({ to: '/recipes/search', search });
},
// _protected/recipes/search: anonymous visitors fall back to the public twin
// (_protected's layout exempted this path from its login-wall redirect via
// location.pathname.startsWith(RECIPES_SEARCH_PATH))
```

- Login redirects preserve the target: guards throw `redirect({ to: '/login', search: { next: location.href } })` (full path **and** query params). The login route parses `{ next, message }` from its search params; `LoginForm` navigates to `next ?? '/recipes'` after success and shows a notice for known `message` keys. **Never drop the `next` param or the query string when adding redirects.**
- Role guards resolve the role from the fetched profile row (`fetchProfile(session.user.id)`), defaulting to `user` when no profile row exists. There is no role override mechanism — the profile row is the only role source.
- Group index routes (`_admin/admin/index.tsx`, `_moderator/mod/index.tsx`) are unconditional `beforeLoad` redirects to the group's dashboard page — safe because the group layout's guard has already verified session and role when the child's `beforeLoad` runs. Nav entries link to the group index (`/admin`, `/mod`) and let the index redirect pick the landing page.
- **One role model for staff areas** (`features/auth/utils/roleAccess.ts`): `canAccessArea(role, area)` and `roleStartPath(role)` are the single source of truth — never inline role checks in guards or nav. `user` → no areas; `moderator` → moderator only; `admin` → both admin and moderator.
- **Role-gated nav between the app and the staff areas:** the protected sidebar appends dashboard entries from `useAuthUser().role` via `canAccessArea` — admins get both "Admin dashboard" (`/admin`) and "Moderator dashboard" (`/mod`); moderators only the latter; users neither. Both dashboard shells carry a first "Back to app" nav entry targeting `RECIPES_SEARCH_PATH`. Wrong-role and anonymous visitors hitting `/admin`/`/mod` are handled entirely by the group guards (login wall with `next`, or redirect to `/recipes`, whose public twin hands signed-in users to `/recipes/search`).
- **Post-login redirect:** `LoginForm` navigates to the login route's `next` param when one exists (deep links win — guards hand it over on every login-wall redirect); with no explicit destination it falls back to `roleStartPath(role)`, where `role` arrives resolved from the fresh session's profile inside the `login` service (`data.role` — a missing profile row falls back to `'user'`). So: user → `/recipes/search`, moderator → `/mod`, admin → `/admin`. The role is resolved before navigating — no flash of the wrong page. Signup keeps navigating to `/verify-otp`.

Filters, sorting, cursor, planner week — shareable view state belongs in the URL via `validateSearch` with a Zod schema whose fields are all optional (parsing never throws):

export const Route = createFileRoute('/_protected/recipes/search/')({

### Loaders and route-level states

- Prefetch in `loader` with the feature's `useXxxOptions` queryOptions factories (`context.queryClient.query(...)`), parallelized with `Promise.all` when there are several (see `_public/recipes/$id`).
- Set `pendingComponent` / `errorComponent` from the feature's exported components — loading and error states are part of the route, not afterthoughts in the page.

## 10. Data Flow Convention

Strict layering, one direction:

```
Component → hook (features/X/hooks) → service (features/X/services) → shared client (src/api/client.ts or src/lib/supabase/client.ts)
```

- **Components never import the clients or call HTTP directly.** They call hooks.
- **Hooks wrap TanStack Query around one service function** — no business logic. Hooks export both `useXxx(params)` and a `useXxxOptions(params)` queryOptions factory (the factory is what route loaders prefetch with).
- **Services own the transport and validation:** they build the Supabase query or axios call, unwrap/normalize the result, and `.parse()` it with Zod before returning. Supabase errors are thrown as `new Error(...)` with a readable message.
- **Endpoint URLs for the REST backend** come from the feature's `api/routes.ts` (`RECIPES_API_ROUTES`, `AI_API_ROUTES`), never string literals in services.
- **The axios client behavior** (don't replicate or bypass it): request interceptor blocks requests with no Supabase session and attaches `Authorization: Bearer <access_token>`; response interceptor refreshes the session once on 401 and replays the request; on final failure it normalizes the backend `{ message }` body into `error.message` (original AxiosError kept as `cause`). UI reads `error.message` — via `getErrorMessage` (`src/utils`) — so users see *why* a request failed.
- **Dexie (local-first) data** — planner, shopping lists, and AI chat history live in IndexedDB (`features/*/lib/*Db.ts`), *by design, not in Supabase*; cross-browser sync happens through a separate encrypted backup blob, not live tables. Even so, reads go through services → TanStack Query hooks with feature query keys (e.g. `plannerKeys.week`, `aiChatKeys.sessions`), so cache/invalidate discipline is identical. Tests run Dexie on `fake-indexeddb`.
- JWT attach/refresh is handled in the client layers. Never touch tokens in components.

### Cursor pagination (list endpoints)

All paginated list endpoints use keyset (cursor) pagination — offset/`.range()`/`page` params are retired:

- **Response contract:** `{ data, nextCursor, hasNextPage }` (`FetchRecipesResponseSchema` in `features/recipes/types/schemas/`). No `total`/`page`/`pageSize` fields; a "results count" UI uses a separate one-shot `head: true, count: 'exact'` query keyed by filters.
- **Params carry `cursor: string | null` and never a `page` field.** Query keys include the filters but **not** the cursor — the cursor flows through `useInfiniteQuery`'s `pageParam`.
- **Technique lives ONCE per feature** (`features/recipes/utils/pagination`): `encodeCursor`/`decodeCursor` (base64 JSON, Zod-validated — cursors arrive from URLs and are untrusted; malformed or sort-mismatched cursors mean "first page", never an error), `SORT_SPECS` (sort column + direction + mandatory `id` tie-breaker; `recent`/`rating`/`time`), and the seek predicate (DESC → `lt`, ASC → `gt`, on the sort column AND `id`, values double-quoted). Fetch `pageSize + 1` rows: `hasNextPage` is the lookahead; `nextCursor` encodes the last returned row only when a next page exists. Schema, sort specs, and select string change together.
- **UI:** "Load more" buttons / infinite scroll — no page-number UIs. Filter changes reset the cursor (a cursor belongs to one result set).
- **Nullability:** `lt`/`gt` never match SQL NULL — a nullable sort column must be excluded by an explicit `.not(column, 'is', null)` filter (documented) or made NOT NULL via a generated column.
- **Every new sort spec ships a composite index migration** `create index on <table> (<sort_column>, id);` (partial when the null filter applies) in `supabase/migrations/`.

## 11. Client State — Zustand v5

For UI-only state: cook-mode check-off, ephemeral view state not in the URL.

- Keep stores small, one per domain, actions inside the store (`features/recipes/store/cookMode.store.ts`). `persist` middleware is used where state must survive reloads.
- **Components never call the raw store hook.** Every piece of store data a component renders gets a small exported selector hook next to the store (`useCheckedIngredients(recipeId)`), re-exported through the feature barrel; actions go through one `useCookModeActions()`-style hook per store. Name hooks after what they return; component-specific defaults are hook parameters (`useRecipeServings(recipeId, baseServings)`), never baked into the store module.
- **Selectors must return stable references.** Never allocate inside a selector (`?? []`, `?? {}`, spreads, `.map()`/`.filter()`) — zustand feeds selectors into `useSyncExternalStore`, which compares snapshots by reference, so a fresh allocation reads as "store changed during render" and can loop. Fall back to a module-level constant next to the hook; wrap genuinely derived objects/arrays in `useShallow` from `zustand/react/shallow`. Primitive fallbacks (`?? 0`, `?? null`) are safe.
- Consume with narrow selectors — never select the whole store; use `useShallow` for object selectors.
- **Never** mirror server data or router state into Zustand. Shared server data belongs in Query; shareable view state belongs in URL search params.

## 12. React 19 + React Compiler

The compiler runs through the Babel pipeline in `vite.config.ts` (`babel-plugin-react-compiler` via `@rolldown/plugin-babel`). **Do not remove or alter that config** — it exists solely for the compiler under Vite 8/Rolldown; removing it silently disables auto-memoization.

- Write straightforward code; no manual memoization.
- The compiler depends on strict adherence to the **Rules of React**: no mutation during render, no ref reads/writes during render, no side effects during render, immutable inputs.
- `eslint-plugin-react-hooks` violations break the compiler. **Never disable or suppress these rules** — fix the code. If a component misbehaves, suspect a Rules-of-React violation first, not the compiler.
- `useEffect` is a last resort. Prefer, in order: events, TanStack Query, router loaders, Mantine hooks, `useActionState` for form submission.

## 13. Server State — TanStack Query v5

All remote data (and local-first Dexie data) flows through React Query, always via feature hooks — never raw `useQuery` in page components.

- **v5 API only.** Object syntax only; `isPending` for "no data yet"; `onSuccess`/`onError`/`onSettled` do **not** exist on `useQuery` (they do on `useMutation`). Many online examples are v4 — check the version.
- Mutations live in hooks too (`useCreateRecipe`, `useUpdateRecipe`, `useDeleteRecipe`) and invalidate in callbacks:

```ts
const qc = useQueryClient();
useMutation({
  mutationFn: updateRecipe,
  onSuccess: () => qc.invalidateQueries({ queryKey: recipeKeys.all }),
});
```

- Mutations show user feedback via `notifications.show` on success; guard preconditions by rejecting the `mutationFn` (e.g. `useCreateRecipe` rejects when `userId` is null).
- Query keys are centralized per feature in `query-keys/` — never inline array literals. Factories nest under an `all` root so one invalidation sweeps the domain.
- Defaults live in `src/lib/query-client/query-client.ts`: `staleTime` 60s, `retry: 1`, `refetchOnWindowFocus: false`. Don't scatter overrides without reason.
- Route loaders prefetch with the same queryOptions factories the hooks use, so loader-filled and hook-read data share one cache entry.

## 14. Mantine v9

- Global styles are imported **once** in `src/main.tsx`: `@mantine/core/styles.css` + `@mantine/notifications/styles.css`, plus `src/styles/globals.css` (AFTER Mantine's styles so token overrides win). `@mantine/modals` ships no stylesheet in v9 — don't add one. Never re-import styles per component.
- Theme: **Meridian** (Linear-inspired) — `src/styles/mantine/theme.ts` (`primaryColor: 'brand'`, indigo `#5e6ad2`, component defaults: Button sm, Input sm + focus ring, Card radius 12, Modal radius 14…) and `src/styles/globals.css` (all design tokens as CSS vars for light + dark, plus the Mantine semantic-variable pins). Raw colors are allowed ONLY in `src/styles/**`; components use the color names `brand / green / yellow / red / pink / gray` (+ `c="dimmed"`) or the `--*` tokens. Icons come from `react-icons/lu` (Lucide). Color scheme via `MantineProvider defaultColorScheme="auto"` + `useMantineColorScheme`/`ColorSchemeToggle` — don't hand-roll dark-mode logic (the no-FOUC script lives in `index.html`).

## 15. Zod v4

**This project uses Zod 4. Do not copy Zod 3 examples — the APIs differ.**

- Top-level format validators: `z.email()`, `z.uuid()`, `z.url()` — not `z.string().email()`.
- `z.record()` requires two arguments: `z.record(z.string(), z.value())`.
- Error customization uses `error:` (e.g. `z.string().min(1, { error: 'Required' })`), not `message:`.
- `z.strictObject()` instead of `.strict()`.
- Formatting issues: `z.prettifyError(error)` / `z.treeifyError(error)`.
- Schemas live in the feature that owns the data (`types/schemas/*.schema.ts`); export inferred types: `type Recipe = z.infer<typeof recipeSchema>`. Shared generated row schemas (Supabase tables) live in `src/types/schemas/supabase/`.
- `schema.parse()` at boundaries (throws); `safeParse()` for user input (collect errors).

## 16. TypeScript Conventions

- No `any`. Use `unknown` + narrow with Zod or type guards. No non-null assertions (`!`) — narrow instead. Never silence the compiler — fix the type or the data flow; never loosen a type (newly-optional fields, casts) to make code compile.
- **`import type` is mandatory for type-only imports** — `verbatimModuleSyntax` is on, so type imports are erased syntactically.
- **`erasableSyntaxOnly` is on** — no TS enums, namespaces, or parameter properties. Use union types / plain objects.
- `strictNullChecks` is on; full `strict` is not — don't rely on that, write strict-safe code. `noUnusedLocals`/`noUnusedParameters` are on; `_`-prefixed names are exempt (the cursor in `recipeListFilters`, unused slots).
- Prefer Zod-inferred types for API data; hand-written types for static domain concepts (following `types/api/`).
- Path aliases (vite + vitest + tsconfig kept in sync): `@api`, `@assets`, `@components`, `@config`, `@features/*`, `@hooks/*` (declared; no such folder yet), `@lib/*`, `@providers/*`, `@routes/*`, `@styles/*`, and `@/*` → `src/*`. Use them; relative `../..` chains are noise.

## 17. Testing

**Vitest + Testing Library + MSW — configured; `docs/TESTING.md` is the full manual.** All network is mocked; tests never touch a real backend or Supabase project.

- Test files are co-located as `*.test.ts(x)` next to the code they cover and are typechecked by `tsconfig.app.json` (so `npx tsc -b` covers them).
- **All network goes through MSW (`src/test/server.ts`), at the network level — never mock axios, the Supabase client, or service modules.** Real interceptors, the real supabase-js client, and all Zod parsing run in every test.
  - `src/test/handlers/rest.ts` — axios REST endpoints (`/ai/*`, `/recipes/import`, …), matching `docs/API_ENDPOINTS.md`.
  - `src/test/handlers/supabase.ts` — PostgREST/GoTrue/Storage simulation over the in-memory store in `src/test/fixtures/tables.ts` (filters, embeds, order, counts, insert returns, RPCs). RPCs are registered in the `rpcHandlers` map.
- `src/test/setup.ts` starts MSW with `onUnhandledFrame: 'error'` — **any request without a handler fails the test.** When a service gains an endpoint, add a handler; don't bypass. Setup also loads `fake-indexeddb` (Dexie), stubs `matchMedia`/`ResizeObserver`/`IntersectionObserver`/`scrollIntoView` (Mantine + `useAutoLoadMore` sentinels), and clears both storages after each test.
- Deterministic fixtures live in `src/test/fixtures/db.ts` (stable ids/timestamps, override-friendly builders — give filter columns *distinct* values). Auth state is controlled by seeding localStorage via `src/test/auth.ts` (`seedSession`/`seedExpiredSession`/`clearSession`) — the storage key supabase-js actually reads; no client internals are touched.
- **Simulating roles in tests:** there is no role override — the profile row is the only role source. Seed it like any other table: `seedSession()` plus `seed('profiles', [profile({ role: 'admin' })])` (builders from `@/test/fixtures/db`, seeding from `@/test/fixtures/tables`); the real supabase-js client fetches the profile through MSW, so guards, nav gating, and post-login redirects all resolve the role exactly as in production (see `routes/_admin.test.tsx`, `routes/_moderator.test.tsx`, `routes/_protected.test.tsx`). To test "role not yet resolved", delay the profile response with a per-test `server.use(http.get(…))` handler instead of mocking the client.
- Component tests render through `src/test/utils.tsx` (`renderRoutes` — real provider stack + memory-history router, fresh QueryClient with `retry: false`). Route integration tests instead wire the **real generated `routeTree`** into a memory-history router and `queryClient.clear()` between tests (see `routes/_protected/recipes/search/index.test.tsx`).
- Query by role/label/text, use `userEvent` (never `fireEvent`), prefer `findBy*` with `{ timeout: 5000 }` for async UI — the 1s default is too tight under the provider stack.
- Simulate failures by overriding handlers per-test with `server.use(http.<method>(…))` and `HttpResponse.json({ message }, { status })`.

## 18. Security rules

- **Only the publishable (anon) key belongs in this app.** It is public by design; RLS is the enforcement layer. Never introduce a `service_role` key, JWT secret, or any server credential client-side.
- **Tokens:** supabase-js persists/refreshes the session; the axios interceptor attaches the Bearer token and blocks unauthenticated requests. Components never read, store, or pass tokens.
- **Never log** env values, tokens, or JWTs. `.env` files are never read, created, edited, or committed by agents.
- **Untrusted input:** URL search params and cursors are attacker-controlled — always Zod-parse (the cursor codec rejects PostgREST `.or()` metacharacters so a crafted cursor can't inject filter syntax).
- Backend owns auth, roles, quotas, plan limits, moderation. The frontend displays what the API returns; it never enforces or works around limits client-side.

## 20. Common Gotchas

- **Copied code from the internet:** check the version. TanStack Query v4 examples (`isLoading` on queries, query callbacks), Zod 3 examples (`z.string().email()`), and Mantine ≤v6 examples (`createStyles`) all look plausible and are wrong here.
- **Duplicating UI between public and protected twins** — the explorer must stay one component (`RecipeExplorerPage`) rendered by both routes; differences are chrome from the layouts, not forks.
- **Dropping state on auth redirects** — `next` must carry `location.href` (path *and* query); twin redirects must forward `search`. Tests exist for both.
- **Redirecting before the session finishes loading** — every guard decision awaits `getSession()`; components show `FullPageLoader` while `useAuthUser().isLoading`. Redirecting on a not-yet-restored session bounces signed-in users to login.
- **Bypassing the shared clients** — no `fetch`, no second axios instance, no second Supabase client. The axios interceptor's error normalization (`{ message }` → `error.message`) is what makes backend failures readable; skipping the client loses that.
- **Mocking axios or supabase-js in tests** — forbidden; the network is mocked at MSW level and unhandled requests fail tests.
- **Stale `routeTree.gen.ts` after adding routes** — expected; the human's dev server regenerates it. Never hand-edit.
- **Cursor in a query key** — never; it flows through `pageParam` or the cache splinters per page.
- **"Optimizations":** `useMemo`/`useCallback`/`memo` wrappers are noise — the compiler handles memoization.
- **Zustand selector allocation loops** — see Client State; return stable references or use module-level constants/`useShallow`.
- **Permission/quota errors** are backend concerns (RLS, plan limits). Don't work around them client-side.
- **Generated files:** `routeTree.gen.ts`, `database.types.ts`, `types/schemas/supabase/schemas.ts` — regenerate via commands, never edit.
